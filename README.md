# Практическая работа №6. Синхронизация

Среда: Windows 11 + WSL2, Ubuntu 24.04, Python 3.12 (только стандартная библиотека).

## Файлы
- `race_buggy.py` - программа с гонкой (потерянные обновления счётчика)
- `race_fixed.py` - исправленная версия (мьютекс, `with lock`)
- `pc_common.py` - общий код: кольцевой буфер на 5 элементов с проверкой инвариантов, запуск 3 производителей и 2 потребителей, итоговая проверка
- `pc_semaphores.py` - производитель-потребитель на двух семафорах и мьютексе
- `pc_condvar.py` - производитель-потребитель на мьютексе и условных переменных
- `pc_condvar_buggy.py` - то же, но `if` вместо `while` (потерянное пробуждение)
- `barrier.py` - барьер на условной переменной, 4 потока, 3 фазы
- `*_output.txt` - реальные выводы программ

## Запуск
- `python3 race_buggy.py` и `python3 race_fixed.py`
- `python3 pc_semaphores.py` и `python3 pc_condvar.py`
- `python3 pc_condvar_buggy.py`
- `python3 barrier.py` и `python3 barrier.py --no-barrier`

Код выхода 0 означает, что все проверки пройдены, 1 - что обнаружено нарушение.

## Гонка и исправление
В `race_buggy.py` 4 потока по 20000 раз делают "прочитать счётчик, записать +1" без
блокировки. Между чтением и записью поток вытесняется (в CPython из-за GIL окно сделано
явным через `time.sleep(0)`), другой поток читает то же значение, и инкременты
теряются: итог намного меньше 80000 (у меня теряется около трёх четвертей). В
`race_fixed.py` чтение и запись выполняются под `with lock`, итог ровно 80000.

## Производитель-потребитель
Буфер кольцевой на 5 элементов, `queue.Queue` не используется. 3 производителя, 2
потребителя, 1000 элементов. Остановка потребителей - по одной метке остановки на каждого.

Корректность проверяется кодом, а не вручную. Внутри критической секции проверяются
инварианты: запись только при count < 5 в свободный слот, чтение только при count > 0 из
занятого слота. Нарушения пишутся в лог. В конце проверяется: все 1000 элементов потреблены,
каждый ровно один раз, посторонних нет, буфер пуст, все потоки завершились (нет
взаимной блокировки).

- Семафоры: `empty` (свободные места, начальное значение 5) и `full` (занятые места, 0)
  блокируют поток, когда ждать нужно; мьютекс защищает только индексы и массив.
  Ожидание на семафоре стоит ВНЕ мьютекса, иначе потребитель удерживал бы мьютекс,
  ожидая элемент, и производитель не смог бы войти - взаимная блокировка.
- Условные переменные: `not_full` и `not_empty` на одном мьютексе, ожидание в цикле `while`.

Обе версии прошли 20 запусков подряд без единого нарушения. Критические секции узкие:
имитация работы (`time.sleep`) находится вне блокировок, поэтому потоки работают параллельно.

## Барьер
Класс `Barrier` на условной переменной с счётчиком поколений. Каждый из 4 потоков
выполняет 3 фазы, после каждой ждёт на барьере. Инвариант: начать фазу k можно, только
когда все 4 потока закончили фазу k-1. С барьером нарушений 0; с флагом `--no-barrier`
проверка фиксирует нарушения, то есть сама проверка работает.

## Потерянное пробуждение (if вместо while)
В `pc_condvar_buggy.py` `while` заменён на `if`. Результат: в каждом запуске 60-95
нарушений ("переполнение: запись N при count=5") и столько же потерянных элементов.

Чередование: буфер полон, производители P1 и P2 спят в `wait`. Потребитель забирает
элемент и делает `notify`, просыпается P1, но должен ещё захватить мьютекс. Пока он
ждёт, в `put` входит не спавший производитель P3, видит свободное место и заполняет
буфер снова. P1 получает мьютекс и, поскольку `if` уже пройден, не перепроверяет условие
и пишет в полный буфер - элемент теряется. К моменту запуска проснувшегося потока
условие уже снова ложно: условная переменная даёт лишь подсказку, а не гарантию, поэтому
условие нужно проверять в цикле `while`. Симметричный случай для потребителей - чтение
из пустого буфера.

## Контрольные вопросы
1. **Чем семафор со значением 1 отличается от мьютекса на практике?**
   У мьютекса есть владелец: блокирует и разблокирует его один и тот же поток (в
   pthreads это обеспечивается), поэтому он подходит для защиты критической секции и
   поддерживает такие вещи, как наследование приоритета. Семафор - счётчик без
   владельца: его может освободить любой поток, поэтому он годится для сигнализации
   между потоками ("событие произошло"), а не для защиты данных. Кроме того,
   неосторожный лишний release поднимает значение семафора до 2, и взаимное
   исключение нарушается. Замечание: `threading.Lock` в Python владельца не
   проверяет, но смысл использования у них разный.
2. **Почему условную переменную нельзя использовать без мьютекса?**
   Проверка условия и уход в ожидание должны быть атомарны относительно изменения
   условия. Без мьютекса возможна последовательность: поток проверил "буфер пуст", ещё
   не успел заснуть, другой поток положил элемент и послал сигнал - сигнал пропал, и
   первый поток заснёт навсегда. `wait` атомарно освобождает мьютекс и усыпляет поток,
   а при пробуждении снова захватывает его. Кроме того, сами разделяемые данные,
   по которым проверяется условие, нужно защищать. В Python вызов `wait` без
   захваченной блокировки вызывает RuntimeError.

## Типичные ошибки (учтено)
- Блокировки используются через `with`, поэтому освобождаются при любом выходе, в том числе при исключении.
- `wait` всегда в цикле `while` (кроме намеренно ошибочной версии).
- Критические секции узкие: вне блокировок остаются ожидание на семафорах и имитация работы.
